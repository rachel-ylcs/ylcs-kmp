这里有几项执行规则，建议从第一轮就固定。

**每轮只解决一种新的不确定性。**  
例如，先证明工件可以显式消费，再做 Bridge 自动替换；先证明单窗口宿主正常，再接导航；先证明基础图片链正常，再加动图和缩放。遇到阻塞时，下一轮缩小为该阻塞的验证任务。

**基础质量检查从前期开始积累。**  
源码锁定、许可证、两平台构建、资源释放和运行记录，从对应能力引入时就开始维护。步骤 18 负责形成完整发行流程，不能把这些工作全部留到最后。

**Windows 与 Linux 分别记账。**  
每项能力分别记录“依赖解析、编译、链接、实际运行、功能验收”。开发时可以先做一端，但进入 Rachel/Gallery 前，应完成两端基础路径。Linux 还需要明确实际验证的是 X11、Wayland，还是两者；无界面 CI 不能替代 IME、GPU 和多显示器测试。

**版本调整与功能接入分开进行。**  
两个参考项目目前的版本基线存在差异，不能直接混用。若较旧组合适合先验证技术可行性，可用于隔离 PoC；接入 Rachel 前仍需解决与合并后仓库的 Kotlin/CMP、源码语法及 API 兼容问题。不要为了跑通 PoC 顺带降低主仓库版本。

**编译范围必须真实可控。**  
图片、媒体或导航模块如果仍被公共源码直接引用，即使界面暂时隐藏，依然可能阻断 Native 编译。优先用独立小示例验证已有组件；确需部分接入真实应用时，再做必要的依赖或源码边界调整。临时替代实现只能记为临时状态。
